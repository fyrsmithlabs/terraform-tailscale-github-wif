# terraform-tailscale-github-wif

Terraform component that declares **Workload Identity Federation (WIF)** trust between
GitHub Actions and a Tailscale tailnet, so a GitHub-hosted runner can join the tailnet
with **no long-lived Tailscale secret stored in GitHub**.

## Purpose

```
workflow (permissions: id-token: write)
  └─ requests a GitHub OIDC id-token for aud = <the Tailscale audience>
       └─ tailscale/github-action@v4 POSTs it to Tailscale
            └─ Tailscale validates iss + aud + sub + the custom claim rules
                 └─ returns a SHORT-LIVED API token (scopes: auth_keys)
                      └─ action mints an ephemeral auth key tagged tag:ci
                           └─ runner joins the tailnet as an ephemeral node
```

The two values a consuming repository needs — the federated identity's **Client ID** and
its **Audience** — are documented by Tailscale as *not secrets* ("These are not secrets and
will be visible in the admin console"). They are module **outputs**, and they belong in
GitHub as repository/org **variables**, not secrets.

Reference: <https://tailscale.com/docs/features/workload-identity-federation>

## Scope model — read before applying

One `tailscale_federated_identity` is created per GitHub **owner** (org or user account),
not per repository. `tailscale_federated_identity` carries exactly one `subject` pattern
and one pattern per custom claim, so per-repo scoping would require one Tailscale trust
credential per repo.

Owner-level trust means **every repository under that owner** that can request an
`id-token` can complete the exchange. What bounds the damage is not the subject pattern —
it is the two knobs below. Keep both minimal:

| Knob | Default | Why it matters |
|---|---|---|
| `federated_identity_scopes` | `["auth_keys"]` | The returned token can mint auth keys and nothing else — it cannot read devices, edit DNS, or touch the ACL. |
| `federated_identity_tags` | `["tag:ci"]` | The only tag the identity may apply. Your tailnet policy grants key off this tag, so it decides what a compromised runner can reach. |

### Subject patterns and the immutable-claim change

GitHub's default `sub` is `repo:<owner>/<repo>:ref:refs/heads/<branch>` (branch pushes) or
`repo:<owner>/<repo>:pull_request` (PRs). Repositories created, renamed, or transferred
after **2026-07-15** use the immutable form
`repo:<owner>@<owner_id>/<repo>@<repo_id>:...`, which a `repo:<owner>/*` pattern silently
stops matching.

This module therefore defaults `subject` to `repo:<owner>*`, covering both shapes, and puts
the real authorization gate in the custom claim rules: an exact match on `repository_owner`
**and** the immutable numeric `repository_owner_id`. A renamed or typosquatted owner cannot
satisfy the id, so the loose subject prefix costs nothing.

- <https://docs.github.com/en/actions/reference/security/oidc>
- <https://github.blog/changelog/2026-04-23-immutable-subject-claims-for-github-actions-oidc-tokens/>

### Ref restrictions

`github_owners[*].ref` pins the OIDC `ref` claim. Leaving it unset is deliberate for most
setups: pinning `refs/heads/main` **breaks pull-request runs**, whose `ref` claim is
`refs/pull/<n>/merge`, not a branch ref. Set it only if you genuinely want branch-push-only
trust and are willing to lose PR CI.

Note that a PR from a fork runs with a `repository_owner` claim of the **upstream** owner,
so a fork PR can satisfy owner-level trust. If you accept fork PRs, either require the
`pull_request_target`-free pattern with manual approval for first-time contributors, or pin
`ref` and accept the loss of PR runs.

### Audience

`audience` is intentionally not settable. Tailscale generates it as
`api.tailscale.com/<client ID>`, which binds it to the client ID — a token minted for one
federated identity is useless against another. Do not hand-pick one, and do not assume it
is the literal string `tailscale`; read it from the `federated_identity_audiences` output.

## Required provider scopes

The Tailscale provider authenticates with an **OAuth client** read from the environment:

| Variable | Value |
|---|---|
| `TAILSCALE_OAUTH_CLIENT_ID` | OAuth client ID |
| `TAILSCALE_OAUTH_CLIENT_SECRET` | OAuth client secret |

The client needs exactly one scope:

- **`federated_keys`** (write) — "read or modify federated identities and keys generated by
  federated identities" (<https://tailscale.com/kb/1623/>)

> **Verify the scope you actually provisioned.** A client created with the console default
> carries scope `all` — full tailnet access including ACL read/write and device management.
> With `all`, a leak of this client is a whole-tailnet compromise rather than a CI-tag
> compromise. Read it back rather than trusting the console UI or this README:
>
> ```
> GET /api/v2/tailnet/-/keys?all=true
> ```

The tag(s) in `federated_identity_tags` must already have a `tagOwners` entry in your
tailnet policy file. **This component does not create tags or grants.**

## Inputs

| Name | Type | Default | Required | Description |
|---|---|---|---|---|
| `github_owners` | `map(object({ owner_id = string, subject = optional(string), ref = optional(string) }))` | — | **yes** | GitHub owners trusted to exchange an Actions OIDC token. Map key is the owner login (matched against `repository_owner`). `owner_id` is the immutable numeric GitHub id and is the real authorization gate — get it with `gh api orgs/<owner> --jq .id` (or `users/<owner>`). `subject` overrides the `repo:<owner>*` default. `ref` pins the `ref` claim. |
| `github_oidc_issuer` | `string` | `https://token.actions.githubusercontent.com` | no | OIDC issuer URL Tailscale validates `iss` against. Identical for every GitHub repo and owner. |
| `federated_identity_scopes` | `list(string)` | `["auth_keys"]` | no | API scopes on the short-lived Tailscale token the exchange returns. |
| `federated_identity_tags` | `list(string)` | `["tag:ci"]` | no | Tags the identity may apply to nodes it authorizes. Must exist in `tagOwners`. |

`github_owners` is validated: every `owner_id` must be numeric. Guessing or leaving a
placeholder fails at plan time rather than silently trusting nothing.

## Outputs

| Name | Description |
|---|---|
| `federated_identity_client_ids` | Map of owner → federated identity Client ID. Set as the `TS_OAUTH_CLIENT_ID` **variable** in each consuming repo. (The provider exposes this as the resource `id`; there is no separate `client_id` attribute.) |
| `federated_identity_audiences` | Map of owner → Tailscale-generated audience (`api.tailscale.com/<client ID>`). Set as the `TS_AUDIENCE` **variable**. |
| `federated_identity_subjects` | Map of owner → the `sub` pattern actually in effect, including the defaulted `repo:<owner>*`. Useful when debugging a rejected exchange. |

## Apply order (human-gated)

1. Ensure the tag(s) in `federated_identity_tags` have `tagOwners` in your tailnet policy.
2. `atmos terraform apply tailscale-github-wif -s <stack>`
3. Read `federated_identity_client_ids` and `federated_identity_audiences` from the outputs.
4. Create the `TS_OAUTH_CLIENT_ID` and `TS_AUDIENCE` **variables** in each consuming repo or
   at the org level. Nothing in this component configures the GitHub side.

## Example Atmos catalog stanza

`stacks/catalog/terraform/tailscale-github-wif.yaml` — provider credentials come from a
declared 1Password secret store (`stores.op` in `atmos.yaml`), never from committed values:

```yaml
components:
  terraform:
    tailscale-github-wif:
      metadata:
        component: tailscale-github-wif
        type: real
      vars:
        # Map key is matched against `repository_owner`; owner_id against the
        # immutable `repository_owner_id` claim. Read the ids from the API —
        # they never change, which is why the id, not the login, is the gate:
        #   gh api orgs/<owner> --jq .id     # organizations
        #   gh api users/<owner> --jq .id    # user accounts
        github_owners:
          example-org:
            owner_id: "000000000"
          example-user:
            owner_id: "000000000"
        # github_oidc_issuer, federated_identity_scopes (["auth_keys"]) and
        # federated_identity_tags (["tag:ci"]) take the component defaults.

      # HUMAN-GATED: create a Tailscale OAuth client with ONLY the
      # `federated_keys` (write) scope and store it in 1Password. Declaring the
      # secrets (rather than `!exec op read ...`) means `atmos secret validate`
      # catches a renamed item or mislabelled field before anything applies.
      secrets:
        vars:
          TAILSCALE_OAUTH_CLIENT_ID:
            description: "Tailscale OAuth client ID — scope federated_keys (write)"
            store: op
            reference: "op://<vault>/<item>/client-id"
            required: true
          TAILSCALE_OAUTH_CLIENT_SECRET:
            description: "Tailscale OAuth client secret paired with TAILSCALE_OAUTH_CLIENT_ID"
            store: op
            reference: "op://<vault>/<item>/client-secret"
            required: true
      env:
        TAILSCALE_OAUTH_CLIENT_ID: !secret TAILSCALE_OAUTH_CLIENT_ID
        TAILSCALE_OAUTH_CLIENT_SECRET: !secret TAILSCALE_OAUTH_CLIENT_SECRET
```

> **Field labels are not standardised.** 1Password item field labels are free-form, and
> hyphenated (`client-id`) vs underscored (`client_id`) labels on two different items is a
> real and easily-missed failure. `atmos secret validate` turns that into a pre-flight
> error instead of a mid-apply one — run it.

## Vendoring with Atmos

`vendor.yaml` in the consuming repo:

```yaml
apiVersion: atmos/v1
kind: AtmosVendorConfig
metadata:
  name: infra-components
spec:
  sources:
    - component: tailscale-github-wif
      source: "github.com/fyrsmithlabs/terraform-tailscale-github-wif.git///?ref={{.Version}}"
      version: v0.1.0
      targets:
        - "components/terraform/tailscale-github-wif"
      included_paths:
        - "**/*.tf"
        - "**/README.md"
```

Then `atmos vendor pull`.
